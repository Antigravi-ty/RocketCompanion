# Global instructions
Limit the amount of comments you put in the code to a strict minimum. You should almost never add comments, except sometimes on non-trivial code, function definitions if the arguments aren't self-explanatory, and class definitions and their members.

Do not remove existing comments unless they are directly related to what you are changing.

## Referring to code in bugs, reviews and commit messages

- **Reference a name, not a position.** This text outlives the code it describes, so cite a selector, function, class, pref or flag name; name a file without a line, and avoid positional phrasing ("the rule above X").

## Code Style
- Our style guide forbids the use of emoji.
- Every file in this repository—including source code, UI strings, comments, console output, documentation, and commit messages—must be written strictly in English.
- **Standalone Commits & Zero Legacy Baggage**: Treat every commit as a standalone version. Do not maintain backward or forward compatibility shims, deprecated fallbacks, dead code, or pure re-export barrel files (`index.ts` facades). Prioritize code clarity, interpretability, and native engineering quality above all else.
- **Self-Explanatory Naming**: All variables, functions, classes, and modules must use clear, semantic, self-explanatory names. Meaningless single-letter or obfuscated identifiers are strictly forbidden, except for standard mathematical and graphics conventions.
- **Neutral Ball Terminology (`No Soccer / Soccar`)**: Never use the word `soccer` or `soccar` (or compound identifiers like `carsoccer` / `car-soccer` / `STANDARD_SOCCAR`) anywhere in source code, UI strings, comments, placeholder domains, tests, or documentation across this repository and its companion submodules. Always use neutral `ball` / `carball` / `arena` terminology (`wss://relay.carball.dev`).

## Architecture Boundaries
- Do not modify any markdown files under the `RCUIModule` submodule (`src/ui-core`). If absolutely necessary, please open an issue or ask first.
- Maintain zero circular dependencies across the codebase.
- Never embed binary or static assets inline in source code via Base64, Data URIs, or byte/hex arrays. Place runtime-fetched static assets in `public/` (mounted as a Git submodule linked to `RocketCompanionStatics`) and co-locate module-coupled binaries with their owning source module.
- `src/physics/core.js` and `src/physics/core.wasm` are auto-generated by Emscripten from the physics C++ source. Do not manually edit or refactor `src/physics/core.js`.
- Maintain unidirectional dependencies: core simulation and engine layers must never import from `src/ui-system` or non-config `src/ui-core` modules (routing UI interaction through `src/game/runtimeUiPort.ts`); `src/ui-core/stores` must only depend on `src/ui-core/config` (never importing from `camera`, `network`, `physics`, `entities`, `game`, or `ui-system`), and `src/ui-core/config` must remain pure configuration without importing runtime subsystems.
- **No Gut-Sharing Splits or Proxy Bloating**: Never split a class by extracting methods into `*Helper.ts` functions, proxy `SubController` classes, state-bag in-place mutators (`sessionState` / `directorCameraState` / `lifecycleCtrl` / `domain` / `ch`), or `Object.assign(this, ...)` state patchers that take the host or state bag and read/mutate >5 of its internal fields, nor bloat host classes with >15 forwarding getter/setter proxy shims. Extract either a pure data pipeline `(inputData) => outputData` or a stateful `SubController` class that owns its own state and exposes a narrow lifecycle interface (`onEnter`, `onExit`, `step`).
- **Strict TypeScript Modules**: All source modules, sub-controllers, and pure data pipelines under `src/` (except `src/physics/core.js`) must be written in `.ts`/`.tsx` with explicit interfaces, avoiding untyped `any` across module boundaries.
- **Pre-Commit Verification**: Always run both the Generation-2 architecture radar and full TypeScript compiler check (`npm run check`, or `npm run radar && npm run typecheck`) before committing, and maintain single-lockfile hygiene (`package-lock.json` only).

## Security & Zero-Credential Invariants
- **Zero Hardcoded Endpoints or Credentials**: Never hardcode real signaling URLs, public or private MQTT/WebSocket broker hostnames (such as `broker.emqx.io`), TURN/STUN credentials, room/topic prefixes, API tokens, or private keys in source code, UI recipes, tests, or docs. Use fictional placeholders (`wss://relay.carball.dev`) and RFC 5737 documentation IPs (`192.0.2.x`, `198.51.100.x`, `203.0.113.x`).
- **Private Profile, Verification Scope & Parameter-Only Public/Custom Brokers**: Keep all official relays and credentials isolated in the untracked private profile repository (synced to untracked `.cache/resolvedProfile.json` via `scripts/syncPrivateProfile.mjs` or imported at runtime as `.rctbnspib`). Default public configs (`PUBLIC_FALLBACK_BROKER_URL`) must initialize with empty strings/arrays; third-party public or custom brokers carry zero SLA or compatibility guarantees, are excluded from official verification pipelines, and may only be supplied externally via runtime parameters (`?publicBroker=`, `VITE_PUBLIC_FALLBACK_BROKER_URL`, or user UI input). Never track `.cache/`, `*.pem`, `*.key`, `*.rctbnspib`, or `.env*`.
